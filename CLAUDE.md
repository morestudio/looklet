# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Looklet (package name `clotheson`) — an AI fitting room. The user picks a model + outfit + accessories + pose + scene, the server asks Gemini or OpenAI to generate a fashion photo, then the browser retouches it (makeup/skin) locally with MediaPipe at no cost. UI text and code comments are in Thai; keep writing comments in Thai to match. AI prompts are written in English on purpose (image models follow English more precisely).

`AGENTS.md` warns that this Next.js (16.4, with `cacheComponents` + `partialPrefetching` in `next.config.ts`) differs from training data — read `node_modules/next/dist/docs/` before using Next APIs.

## Commands

```
npm install
npm run dev      # dev server, bound to 127.0.0.1 only (port in package.json scripts) so no one on the LAN can use our API keys
npm run lint     # eslint
npm run build && npm start
```

There are no tests. Requires Node >= 20.9.

`.env` (gitignored) holds `GEMINI_API_KEY` and/or `OPENAI_API_KEY`; restart the dev server after editing. Models only appear in the UI when their provider key is set (`availableModels()` in `lib/ai.ts`).

## Architecture

**Client / server split.** `components/TryOn.tsx` is the single client page (`app/page.tsx` just renders it). It calls our own `app/api/*` routes via `api()` in `lib/browser.ts`; API keys never reach the browser. Server-only modules import `'server-only'` (`ai.ts`, `prompts.ts`, `storage.ts`, `genlog.ts`, `route.ts`). POST routes are wrapped with `post()` from `lib/route.ts`, which parses JSON and turns `ApiError` (an AI provider error) into a 502 and other errors into a 500, with a message the UI shows directly.

**Generation flow (`app/api/generate/route.ts`).** The browser downscales each selected image to a JPEG ≤1024px (`jpegBase64`) and posts base64 data. The route builds one ordered `inputs` list — model (required), outfit, accessories (max `MAX_ACCESSORIES`), pose, scene — used for both the AI call and the log. **Image order must match the "Image n" references in `buildPrompt()` (`lib/prompts.ts`)**; changing one requires changing the other. `poseMode` (`POSE_MODES` in catalog) controls whether the pose image supplies only the pose or also the camera/lighting/scene ("shot-scene" drops the selected scene). With a pose photo, `buildPrompt` always adds rules that came out of side-by-side tests: don't copy the model photo's frontal head angle, take the expression from the pose photo (`FACE_MOODS` 'auto') or the chosen mood, and keep the pose photo's clothing (including hems on the floor) out. In copy-the-shot modes the route first asks a cheap vision model to describe the reference lighting (`describeLighting` in `lib/ai.ts`) and adds it to the prompt, unless the user picked a preset's light (`LIGHT_SOURCES` 'preset' → `presetLightPrompt`). Uploaded scene photos get the same treatment (`sceneLight`), so the model is lit like the real room instead of with invented dramatic shadows. An optional second "harmonize" pass re-runs the result through `harmonizePrompt`. The result is saved immediately (it's already paid for), then logged. **Pose presets** (`POSE_PRESETS` + `POSE_AUTO` in catalog; the pose step's ท่าสำเร็จรูป section): with no pose photo, the route asks a small planner model (`planPose` in `lib/ai.ts`, GPT-6 Luna, Gemini Flash fallback) to look at the scene photo (or scene text, or the model photo's background), outfit and accessories and write one pose for that exact place following the preset's brief plus one of its `moments` picked at random per generation (`pickMoment`; without it the planner repeated the same pose every time, so keep concrete examples out of `brief` and put them, including the body position, in `moments`); the English plan goes into the prompt (`posePlan`), the Thai plan is returned and saved with the image. If planning fails the old autoPose wording is used. **Photoshoot set** (`SET_SHOTS` in catalog, `generate(true)` in TryOn): the first shot is generated normally, then the other angles are generated in parallel through the same route with `set_ref` (the first result) + `set_shot`, which switches to `buildSetPrompt` (image order: set ref, model, outfit, accessories; no pose/scene images).

**Output size.** GPT Image 2.5 models generate at 1664×2496 by default (`GPT25_SIZES` in `lib/catalog.ts`; the page still sends the standard size for the image's orientation and the route maps it). Those PNGs are ~6 MB, over the 4.5 MB a Vercel function can return, so results larger than 3.5 MB are saved as JPEG quality 97 (`servable` in `lib/images.ts`, `sharp`); lower JPEG quality measurably smooths skin texture. The skin refine route (`app/api/refine-skin`) uses the same sizes.

**AI providers (`lib/ai.ts`).** Model ids are `"<provider>:<model>"`. Gemini uses `generateContent` with `responseModalities: ['IMAGE']`; OpenAI uses `/v1/images/edits` with `input_fidelity: 'high'` and automatically retries without it for models that reject it. `describeAccessory()` auto-classifies uploaded accessories (Gemini first, then OpenAI) into `ACCESSORY_TYPES`.

**Catalog (`lib/catalog.ts`).** Static choices: built-in images in `public/images` (Thai filenames, URL-encoded via `img()`), plus `PRESETS` (shoot presets: each part — light, lens, angle, framing, color, and an optional `scene` — has a Thai `label` shown in the UI and the English `prompt` actually sent, so the UI always matches the prompt; the first preset, Looklet signature, is the default: Studio lookbook's light and neutral color plus a 3/4 framing and a super-minimal scene instruction, which `presetPrompt` appends but `presetLightPrompt` (copy-the-shot modes) leaves out). Framing and camera angle are also their own steps (ระยะ / มุมกล้อง, `FRAMINGS` / `ANGLES`): 'ตามสไตล์' keeps the preset's own, a choice replaces the preset's `framing`/`fullBody` and is passed to `presetPrompt` as the angle; copy-the-shot modes and the photoshoot set ignore them. A chosen framing/angle is also sent as `camera` to `buildPrompt`, which repeats it as the last, most important line and stops the pose photo's framing and the scene photo's eye level from overriding it (without this GPT ignored the choice). With a pose photo and a close framing, the legs outside the frame are cropped (the default stays full body). Placement (ตำแหน่ง step, `PLACEMENTS`): left / center / right as chosen, or for อัตโนมัติ the route picks left / right / no instruction (about 40/40/20) per image (`pickPlacement`) and `buildPrompt` says it in the first line and again near the end (`placementLine`); without it GPT centers the person in nearly every image. Copy-the-shot modes, outfit-only changes and later set angles get no placement and smaller prompt-fragment lists (gazes, props, accessory types with `prompt`/`show`/`face`). User-uploaded items come from `/api/library` and are merged with these in the UI; items are identified by `src` (or by `name` for text-only scenes), never by index.

**Product page (`/product`, `components/Packshot.tsx`).** A second page for product packshots, switched with `PageSwitch` (`components/ui.tsx`) in both headers, same layout and CSS as TryOn. Choices live in `lib/packshot.ts` (product types, `SETS`, `BACKDROP_COLORS`, `PROP_STYLES`, lights, angles, framings, and 9 `PRODUCT_PRESETS` derived from the user's 11 sample packshots); the browser sends only ids ('preset'/null = the preset's own part) and `app/api/packshot/route.ts` turns them into the prompt with `buildPackshotPrompt` (`lib/packshot-prompts.ts`). **Image order: product, then the reference shot (ช็อตต้นแบบ), then the set photo** (set angles: first result, then product); it must match the "Image n" references. A reference shot is used in one of `REF_MODES` (copy the whole shot / set + light / light only). The fidelity rule says the product photo is for the design only, never the camera angle, and `PRODUCT_ANGLES` describe how far the product is turned and what is (not) visible; without both, every angle came out as the upload's flat front view (user test 26 Oct). Props other than none go through `planStyling` (`lib/ai.ts`, same planner models as `planPose`) with a random `moment`. OpenAI can't make 4:5 or 9:16, so the route generates the nearest size and centre-crops (`cropTo` in `lib/images.ts`). Products are classified on upload by `describeProduct` (`/api/detect-product`). Uploads use their own kinds (`products`, `product-refs`, `product-scenes`), results are tagged `page: 'product'` and each page shows only its own history; logs use `PackshotLog`. No face/skin retouch here, only the `lib/film.ts` look.

**Storage (`lib/storage.ts`).** With Supabase env vars it delegates to `lib/storage-supabase.ts` (private `images` bucket + `images` table, `supabase/schema.sql`; reads check the table row first because Supabase's CDN keeps deleted files for an hour). Otherwise everything is local files: generated images go to `results/`, uploads to `images/uploads/<kind>/`, and each image has a sidecar `.json` with its metadata. Images are served through `/api/files/...` (not `public/`, which doesn't see files added at runtime); `resolveFile` guards against path traversal. Delete moves files to `~/.Trash`. Keep the `saveImage / listImages / readImage / updateMeta / deleteImage` interface stable; routes only use these.

**Auth (only when Supabase env vars are set).** `proxy.ts` (Next 16's replacement for middleware) refreshes the Supabase session and sends non-members to `/login` (pages) or 401 (`/api/*`); every API route checks again via `signedIn()` in `lib/route.ts`. Membership is `app_metadata.looklet === true` (`isMember` in `lib/auth.ts`), set only with the secret key by `scripts/add-user.mjs` — there is no sign-up page. Without Supabase env vars, auth and Supabase storage are both off and the app behaves as a local-only tool.

**Generation logs (`lib/genlog.ts`).** Every generation (success or failure) writes `logs/<same name as result>.json` (or `<stamp>-error.json`), with sections `ai / model / element / pose / style / prompt`. Read these to debug what was actually sent to the AI.

**Retouching (browser only).** `lib/film.ts` runs last on every generated image, so downloads include it, and needs no MediaPipe. It has two looks: `film` (soften + luminance grain, magazine look) and `phone` (tuned against a real iPhone photo: slightly more contrast, less saturation, faint shadow noise, no softening). Each result stores the look that suits it (`finish`, set at generation: Phone candid → phone, else film), and the retouch step's 'อัตโนมัติ' uses it. `lib/vision.js` loads MediaPipe FaceLandmarker + ImageSegmenter (the wasm version must match `@mediapipe/tasks-vision` in package.json) and is loaded with dynamic `import()`. `lib/beauty.js` holds the pure pixel algorithms (RGBA arrays, 478-point face mesh indices). `components/useRetouchCanvas.ts` applies the slider amounts to a canvas. Pasting the real face from the model photo is disabled by the `REAL_FACE` flag in `TryOn.tsx`; the code is kept so it can be re-enabled (see the comment there for why).

`results/`, `images/uploads/`, `logs/` and `.env*` are gitignored.

**Product shot workflow.** `/product` starts with product → shot type. `SHOT_TYPES` in `lib/packshot.ts` defines Clean, Multi-angle, Detail, Scale and Styled (shown as “Custom Packshot”; Creative is “Creative Packshot”). For the first launch only `OPEN_SHOT_TYPES` in `Packshot.tsx` (Clean, Custom, Creative) can be picked; the others stay visible but greyed out (“เร็วๆ นี้”), with their UI/API/tests intact. The rail always shows every step in a fixed order like the model page; steps the shot type doesn't use (`stepUsed`) are greyed out and skipped by “ถัดไป”. Custom has no สไตล์ step (removed 27 Oct): the chosen scene brings its matching preset (`scenePreset` in `lib/packshot.ts`: grade plus default light/angle/framing, shown as “ตามฉาก”), and the client sends that preset id. Props do not follow the scene: the พร็อพ step has no ไม่มีพร็อพ / ตามฉาก / AI เลือกให้ cards (the API still accepts `auto`); nothing selected = no props, clicking the selected style again clears it, and the user picks either one style or พร็อพของฉัน, never both (`chooseProp` / `select('prop')` clear the other; the API can still combine them). Custom's ฉากและพื้น step shows only ใช้รูปฉากของฉัน then ตัวเลือกฉาก (no colour picker or preview; the colour stays `match`); the พร็อพ step shows พร็อพของฉัน then ตัวเลือกพร็อพ. The ตั้งค่า step has no light picker (removed 27 Oct): the light always follows the scene (`light: null` → `sceneLightId`/preset light); the API still accepts `light`. The ช็อตต้นแบบ step is hidden by `REF_SHOT = false` in `Packshot.tsx` (its UI/API code is kept). Props: 23 `PROP_STYLES` shown in `PROP_GROUPS` (every style except none must be in exactly one group; existing ids such as `fruit`/`atelier` are used by presets, so keep them). “พร็อพของฉัน” (Custom only) adds a typed prop (`prop_text`) and/or a photo from the `product-props` upload library (`prop_image`) (alone in the UI; the API also supports it on top of a style). The prop photo is sent after the scene photo and before the extra product photos (`hasPropImage` in `buildPackshotPrompt`), and the planner (`planStyling` `ownProp`/`propImage`) builds the other props around it. Other props are always unbranded; the user's own prop keeps its print. Prop composition (fixed 27 Oct after props came out as one small object pushed to the frame edge): `planStyling` asks for 2–4 on-theme props forming one tight group with height and depth (one substantial prop or a riser, small loose items only as accents, nothing borrowed from other styles, everything inside the frame), the image prompt centers the product-plus-props group instead of the product, and `PRODUCT_FRAMINGS[].withProps` shrinks the product (medium 60→50%, close 85→75%) when props are on. Tested side by side on 3 real cases before integrating. Non-styled types use clean studio defaults, accurate colors and no film finish. Clean/Multi constrain backgrounds to seamless and remove props; Detail selects a macro target; Scale requires positive width/height/depth in cm and laptop body dimensions when used. Multi generates Front first, then Back/Side/45° with optional Top/Bottom; each later view uses the first result for consistent styling. Up to five additional same-product photos are appended after the existing image inputs, with their exact indices referenced in the prompt. The API enforces shot constraints and validates size data before AI calls. `node scripts/test-packshot-workflow.mjs` verifies these paths using mocked AI/storage, without paid generation.

**Product camera angles.** `shotAngles` and `resolveProductAngle` in `lib/packshot.ts` share the camera rules between UI and API. Clean offers front/45°/side/back/top/bottom; Styled offers preset/front/45°/side/slightly-above/flat-lay/low. Old high-angle preset defaults resolve to slightly-above. Detail chooses camera orientation from the selected feature; Scale uses a straight, level camera for hand/person/laptop and overhead for A4. These automatic modes ignore manual angle overrides in API requests. Multi keeps angle selection in the shot-type step. Camera cards include a product/camera diagram and legend.

**Product backgrounds.** The “ฉากและพื้น” step uses schematic scene cards, compatible palettes, and a combined scene/color preview (not a generated result). `resolveProductBackground`, `shotSets`, and `sceneColors` share the constraints between client and API: Clean/Multi use seamless white/light-grey/cream, Detail uses a quiet neutral background with soft blur, Scale auto-selects studio for hand/person and tabletop for A4/laptop. Styled allows all scenes and uploads. Scene changes recommend matching lighting; explicit manual light overrides persist. Uploaded scenes use their own described light, perspective and contact-shadow instructions instead of an additional studio lighting command.

**Product output.** The product page no longer has a “ลุคภาพ” step or before/after look button. All shot types preview and download the generated image without browser film/phone effects (`NO_FILM`); new product requests store `finish: off`. The model page retains its own finish controls.

**Product photo groups.** `lib/product-groups.ts` groups product uploads by `productGroup` (the first photo's stable URL). Group name/type/main-photo metadata lives on that first upload, independently of its photo membership, so moving or removing it does not delete the group. Old uploads remain independent products until explicitly moved. `/api/product-groups` validates membership before edit/main/view/move/remove/restore operations; removal is recoverable metadata (`productRemoved`) and does not delete the source file or group metadata. `/api/upload` validates the destination group for additional photos. `ProductLibrary` shows one cover card per product, photo counts, a dedicated additional-photo upload, view labels, moving and restoration. Generation automatically selects the main photo plus at most five same-group references (`productSources`), preferring the requested angle/detail. `node scripts/test-product-groups.mjs` tests routes against real temporary local storage without touching user data; the existing Supabase JSON metadata interface is unchanged.

**Simplified product upload UI.** `ProductLibrary` now offers one multi-file upload: one file selection creates one product group. `Packshot.onProductFiles` identifies the first valid photo, saves it as the group root, then explicitly attaches the remaining files to that same ID (not the previously selected product). Adding to an existing group uses its captured ID for the whole batch. Layout (revised 27 Oct because users found it confusing): the selected product sits on top (“สินค้าที่ใช้”: cover, name with ✎ rename, all photos with a “รูปหลัก” tag, × to remove a photo when it has more than one, a “เอากลับ” undo, and “+ เพิ่มรูปมุมอื่นของสินค้านี้”), then “+ เพิ่มสินค้าใหม่”, then “สินค้าของฉัน” newest first with no scroll box. The UI never says “กลุ่ม”. Rename/remove/restore use the existing `/api/product-groups` actions (`edit`, `remove`, `restore`) via `editGroup` in `Packshot.tsx`; view/move/main controls and product-type forms are not shown. Upload failures keep successfully saved photos and report the partial result. Existing grouping metadata and API remain compatible.

**Creative Shot.** A sixth product shot type (shown as Creative Packshot) provides a short rail: product → shot type → ไอเดียภาพ → settings. `CreativeShot` is one screen with no method choice (the old AI / inspiration / brief modes were removed 27 Oct as the most confusing part): optional “ช่วย AI คิด” inputs (idea text, inspiration image from the `product-refs` library, collapsed product facts) that can be combined, one red “ให้ AI คิด 3 ไอเดีย” button, then “เลือก 1 ไอเดีย” cards; the selected card shows scene/props/light/composition and a “สร้างรูปจากไอเดียนี้” button. UI wording is always “ไอเดีย”, never “คอนเซปต์”. `/api/creative-concepts` no longer takes `mode`; `idea` and `inspiration` are both optional. `/api/creative-concepts` uses the existing vision planner (`planCreativeConcepts` in `lib/ai.ts`) to return three distinct validated concepts with Thai summaries, palettes and scene/prop/light/composition details plus one English art-direction prompt. Product references precede optional inspiration; ingredient/scent/benefit claims must not be inferred from appearance. “คิดไอเดียใหม่” passes previous titles and rejects repeats. Concept selection is bound to the product's photo group, mode and brief/facts/reference; changed inputs invalidate selection. Generating requires a valid selected concept. `buildCreativePackshotPrompt` uses that concept as the only art direction, without appending conflicting packshot presets; selected title and summary are retained in captions and `stylePlan`, full prompts in logs. `node scripts/test-creative-concepts.mjs` mocks provider HTTP calls to verify planner behavior without charges; packshot workflow tests cover creative generation and validation.

**Localized model edits (“แก้เฉพาะจุด”).** A button beside saved model results opens `LocalEditDialog`, which displays the full-resolution original before browser retouch/film. Pointer brush strokes select an area; eraser, undo, clear (undoable), brush size and inward edge feathering are supported. The client exports a same-size PNG alpha mask (transparent = editable) and sends only mask, source result URL, prompt and supported OpenAI model to `/api/local-edit`. The authenticated route reads the stored original, validates the mask/size/nonempty selection before any provider call, and passes it through `generateImage`'s optional `mask` option. OpenAI input-fidelity fallback retains the mask; non-OpenAI mask calls are rejected. `prepareLocalEdit` normalizes source orientation; `blendLocalEdit` resizes the provider result to source dimensions and blends strictly inside the selection with inward feathering. Erased holes/outside pixels are copied byte-for-byte in decoded RGBA. Save as lossless PNG with `editedFrom` and `finish: off`; originals remain in history with a “ดูต้นฉบับ” button. Edited results also export PNG from the browser instead of JPEG. `/api/files` streams files above 3.5 MB, so large lossless outputs do not require lossy re-encoding. `node scripts/test-local-edit.mjs` verifies pixel invariants, source orientation, validation, provenance, provider retry/mask behavior and large-file streaming without paid generation.

**Localized product edits.** Packshot results also open the shared `LocalEditDialog`. `/api/local-edit` inherits `page: product` and `stylePlan` from the stored source metadata, including repeated edits, so new images remain in product history after reload. Product prompts preserve packaging, labels, logos and product proportions unless explicitly changed. Edited variants are separate history entries rather than additional angles in the original set; the source remains accessible through “ดูต้นฉบับ”. Preview/download use lossless PNG for edited results.

**Rough localized edits (default).** `LocalEditDialog` now defaults to “ไฮไลต์คร่าว ๆ”, where a partial highlight is a visual pointer, not an object segmentation or pixel boundary. The API receives explicit `mode: rough`; old requests without mode retain precise behavior. The server builds a translucent-red guide from the validated mask and sends clean source first, guide second, with no API mask. The prompt targets the entire indicated object, including straps, preserves design for recoloring, and excludes guide marks. Rough results are normalized to source dimensions and saved as PNG without brush-based compositing; nearby details can change, disclosed in UI. “ระบายแบบละเอียด” retains exact outside-mask pixel preservation and feather control. Both model/product pages use the shared dialog. Tests verify two ordered input images, annotation construction, no mask even on retry, changes beyond rough strokes surviving save, validation, and product provenance.
